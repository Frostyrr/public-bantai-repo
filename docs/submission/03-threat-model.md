# Appendix B — Threat Model

**System:** Bantai – Organization Finance Management System

C = Confidentiality, I = Integrity, A = Availability.

| # | Threat | Vulnerability | Countermeasure | CIA | How I Tested It |
|---|---|---|---|---|---|
| 1 | Attacker injects SQL to bypass login or steal data | Putting user input directly into SQL queries | Parameterized queries and prepared database functions everywhere, plus server input checks | C, I | Typed `' OR '1'='1` in login; rejected with no SQL error and no login |
| 2 | Attacker runs scripts in another user's or admin's browser (XSS) | Showing user input or log text as raw HTML | React escapes all displayed text (including dashboard logs), and server blocks `<` and `>` in names | C, I | Typed `<script>alert(1)</script>` as login username, opened Admin Dashboard; shown as plain text with no pop-up |
| 3 | Fake website submits requests using a logged-in user's browser (CSRF) | Trusting requests without checking origin or token | Protected routes require an explicit Bearer token header and allowed origin; public forms require server-checked Turnstile CAPTCHA | I | Removed CAPTCHA/auth header using browser tools and submitted; server rejected the request |
| 4 | Attacker checks which usernames exist (Username Enumeration) | Showing different errors for unknown user vs. wrong password | Login and Forgot Password return the exact same message ("Invalid username or password.") whether or not the account exists | C | Compared wrong username vs. wrong password side by side; both gave the same message and status |
| 5 | Attacker guesses passwords or attacks many accounts from one IP | Unlimited login attempts | Server lockout: 3 fails = 15s, 6 = 30s, 9 = 60s; 10 fails in 10 min from one IP blocks that IP for 10 min | C, A | Failed 3 times (locked 15s even after reload) and 10 times across accounts from one IP (IP blocked) |
| 6 | Someone uses an unattended computer or clicks Back after logout | Sessions never expire or pages stay cached in browser | 15-minute idle timeout with 1-minute warning, server revokes session on logout, `Cache-Control: no-store` on protected responses | C, I | Stayed idle 15 min (warned at 14 min, logged out at 15); clicked Back after logout and was sent to login |
| 7 | User changes password back to an old or leaked password | System does not remember past passwords | Database stores hashes of the last 3 passwords and blocks reusing any of them | C | Tried changing password to the current password; server rejected it with "You cannot reuse a recent password." |
| 8 | Bots spam the registration form | Public signup form has no hidden bot check | Hidden honeypot field on registration that humans cannot see; if filled, server silently rejects it | I, A | Filled the hidden field using browser DevTools and submitted; account was not created |
| 9 | Attacks happen without anyone noticing | No record of login failures, lockouts, or admin actions | Append-only `security_events` table logs all login, OTP, lockout, IP block, reset, and admin events with time, IP, and browser | I, A | Triggered failed logins, lockouts, and dashboard views; checked that every event appeared in the log |
| 10 | Raw server or database errors leak system internals | Showing stack traces or SQL errors to users | Central error handler returns clean, plain messages to users and keeps real error details in server logs only | C | Sent broken input and bad IDs to API routes; got clean JSON error messages with no stack trace or SQL text |
| 11 | Passwords, SMTP keys, or encryption keys leak on GitHub | Putting secrets in code or committing `.env` files | All secrets live in local `.env` files listed in `.gitignore`, never in Git or frontend code | C | Checked `git log` and tracked files; zero passwords, API keys, or encryption keys found |
| 12 | Clickjacking or MIME-sniffing attacks | Missing security headers on responses | Helmet sends `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff` on responses | C, I | Checked response headers in browser DevTools Network tab; both headers were present |
| 13 | Database leak exposes sensitive contact info in plain text | Saving sensitive retrievable fields unencrypted | Enrolled MFA email is encrypted at rest using AES-256-GCM with a random IV; decrypted only on the server for the owner | C | Checked `email_mfa` table in database; only unreadable ciphertext is stored, while owner sees their contact in settings |
