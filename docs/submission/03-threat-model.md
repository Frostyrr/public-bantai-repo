# Appendix B — Threat Model

**System:** Bantai — Collaborative Financial Management System for Organizations  
**Course:** IT 107 · Information Assurance and Security 1 (Criterion P3 / CO2)

This Threat Model maps all **13 required protections** from Section 12 of the IT 107 handout to their corresponding threats, underlying vulnerabilities, countermeasures implemented in Bantai, primary **CIA Triad** pillar(s) defended (**C** = Confidentiality, **I** = Integrity, **A** = Availability), and verification results.

| # | Protection | Threat | Vulnerability | Countermeasure in Bantai | CIA | How I Tested It |
|---|---|---|---|---|---|---|
| 1 | **SQL Injection** | Attacker injects malicious SQL through login, registration, or search inputs to bypass authentication or exfiltrate/modify records. | Concatenating untrusted user input directly into SQL query strings. | All database queries use parameterized PostgREST filters and strongly typed PostgreSQL RPCs (`bantai_login_restriction`, `resolve_login_username`, `bantai_sq_action`, etc.) with `set search_path = ''` and Zod input validation before execution. | **C, I** | Submitted `' OR '1'='1` as the login identifier; Express Zod validation rejected it with `400` and parameterized RPC lookups produced zero SQL errors and no unauthorized sign-in. |
| 2 | **Cross-Site Scripting (XSS)** | Attacker injects `<script>` or HTML payloads into profile fields or login usernames (stored in `LOGIN_FAILED` logs) to hijack admin or member sessions. | Rendering untrusted input or attacker-controlled log values as raw HTML without escaping. | React escapes all JSX text nodes by default across forms and the Admin Security Dashboard; backend validators (`personName`, `displayName`) reject control characters and `<` / `>`; strict Helmet CSP (`default-src 'none'`, `frame-ancestors 'none'`) is enforced on API responses. | **C, I** | Entered `<script>alert(1)</script>` as a login username and opened the Admin Security Dashboard; the payload rendered strictly as inert literal text with no script execution. |
| 3 | **Cross-Site Request Forgery (CSRF)** | Malicious third-party site tricks an authenticated user's browser into submitting unauthorized state-changing requests (e.g., approving expenses or changing settings). | Relying solely on ambient cookies for state-changing requests without origin or token verification. | Authenticated API endpoints require an explicit `Authorization: Bearer <jwt>` header (never ambient cookies), strict CORS origin allow-listing (`env.APP_ORIGIN`), and server-side Cloudflare Turnstile challenge verification on public auth/inquiry forms. | **I** | Sent a cross-origin POST request without the `Authorization` bearer header / stripped the Turnstile token via browser DevTools; Express rejected the request (`401` / `400`). |
| 4 | **Username Enumeration** | Attacker probes login, registration, or forgot-password endpoints to discover valid usernames/emails for targeted credential stuffing or phishing. | Returning distinct error messages (e.g., "User not found" vs. "Wrong password") or skipping work for nonexistent accounts. | `/auth/login` resolves unknown usernames to a synthetic invalid address (`unassigned-username@example.invalid`) and always returns the identical generic message `"Invalid username or password."`; `/auth/register` returns a neutral message for existing emails; Forgot Password returns uniform responses regardless of account existence. | **C** | Compared status codes and response bodies for a nonexistent username vs. a valid username with a wrong password side by side; both returned `401` with `"Invalid username or password."` |
| 5 | **IP Blocking & Progressive Lockout** | Attacker runs automated credential-stuffing or brute-force attacks across one or many accounts from a single IP or distributed sources. | Unlimited authentication attempts without server-side rate limiting, account lockouts, or IP-level blocks. | PostgreSQL `bantai_record_login_failure` enforces progressive per-account lockouts (3 failures → 15s, 6 → 30s, 9 → 60s) and blocks any IP reaching **10 failures in 10 minutes** across any accounts for 10 minutes in `public.source_restrictions`, reinforced by Express `enforceSourceRestriction` and Redis rate limiters (`429` + `Retry-After`). | **C, A** | Simulated 3, 6, and 9 consecutive failures (verified exact 15s / 30s / 60s server-enforced lockouts that survived page reload/cookie clearing) and 10 failures across multiple usernames from one IP (verified `IP_BLOCKED` event and 10-minute restriction). |
| 6 | **Session Hardening** | Attacker hijacks an unattended terminal, replays a logged-out session via the browser Back button, or exploits session fixation. | Long-lived sessions without idle expiry, cached protected pages, or missing server-side revocation checks. | Server-side session tracking in `bantai_private.sessions` enforces a **15-minute idle timeout** (`idle_seconds = 900`) with a 1-minute warning (`X-Session-Idle-Remaining <= 60`), `Cache-Control: no-store` on all authenticated responses, server-side revocation on logout, and full client query cache clearing on sign-out. | **C, I** | Left an authenticated session idle until minute 14 (observed warning banner) and minute 15 (automatic sign-out); after logout, pressing the browser Back button redirected to `/login` with no protected data exposed. |
| 7 | **Password History** | Compromised user resets their password back to the same or recently leaked password, defeating the purpose of rotation. | Allowing immediate reuse of previous passwords during Forgot Password or Account Settings password changes. | `bantai_private.password_history` stores salted hashes of the user's **last 3 passwords**; `passwordHistory.service.ts` verifies every new password against stored history before committing any password update and rejects matches with `"You cannot reuse a recent password."` | **C** | Attempted to change a test account's password to its current password and a previously used password; both were rejected server-side without modifying the account credentials. |
| 8 | **Honeypot (Bot Trap)** | Automated scripts spam the registration form with fake accounts. | Public signup forms lacking invisible bot traps alongside CAPTCHA. | Registration includes an off-screen hidden honeypot field invisible to human users; any submission with a populated honeypot field is silently rejected server-side without creating an account, paired with server-verified Turnstile CAPTCHA. | **I, A** | Populated the hidden honeypot input via browser DevTools and submitted the registration form; the server refused account creation silently. |
| 9 | **Activity Logging** | Attacks, brute-force waves, or unauthorized admin access go unnoticed because no forensic trail exists. | Missing or incomplete logging of authentication, lockout, OTP, recovery, and administrative events. | `public.security_events` records `REGISTERED`, `ACCOUNT_VERIFIED`, `LOGIN_SUCCESS`, `LOGIN_FAILED`, `OTP_SENT`, `OTP_FAILED`, `LOCKOUT_TIER_1/2/3`, `IP_BLOCKED`, `ALERT_EMAIL_SENT`, `RESET_REQUESTED`, `PASSWORD_CHANGED`, `CAPTCHA_FAILED`, `ADMIN_VIEWED_DASHBOARD`, and `ADMIN_ACCESS_DENIED` with timestamp, IP, user-agent, and metadata. | **I, A** | Executed login failures, lockouts, OTP checks, and dashboard opens; verified each corresponding event row appeared in `public.security_events` and the Admin Security Dashboard. |
| 10 | **Error Handling** | Attacker triggers unhandled exceptions to leak stack traces, database table names, SQL syntax, or internal file paths. | Returning raw database or framework errors directly to HTTP clients. | Centralized Express `errorHandler.ts` maps domain `AppError` and Zod errors to clean user-facing messages and returns a generic `500` message for unexpected failures; full diagnostic details stay in server logs only. | **C** | Sent malformed JSON, invalid UUIDs, and out-of-range query parameters to API routes; responses returned clean JSON error messages with zero stack traces or SQL error strings. |
| 11 | **Secrets Management** | API keys, database service role keys, SMTP passwords, or encryption keys leak into Git history or client bundles. | Hardcoding secrets in source code or committing `.env` / config files to version control. | All secrets (`SUPABASE_SERVICE_ROLE_KEY`, `BREVO_API_KEY`, `SMTP_PASS`, `TURNSTILE_SECRET_KEY`, `EMAIL_MFA_ENCRYPTION_KEY`, `EMAIL_MFA_HMAC_KEY`) live exclusively in local gitignored `.env` files validated by `backend/src/constants/env.ts`; `.env*` is blocked in `.gitignore` and never bundled into `frontend/`. | **C** | Audited `git log`, `git ls-files`, and frontend `dist/` bundles; confirmed zero live credentials, SMTP passwords, or encryption keys exist anywhere in Git history or client assets. |
| 12 | **Security Headers** | Attacker embeds the login page in a hidden `<iframe>` (clickjacking) or tricks the browser into MIME-sniffing uploaded content as executable script. | Missing defensive HTTP response headers on web pages and API responses. | Express configures `helmet` with `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, restrictive CSP (`frame-ancestors 'none'`), and disables `X-Powered-By`; frontend deployment headers mirror these protections. | **C, I** | Inspected HTTP response headers in browser DevTools Network tab; verified `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store` on authenticated API responses. |
| 13 | **Encryption at Rest (AES-256)** | Database dump or unauthorized read exposes sensitive user contact/reference values in plaintext. | Storing sensitive retrievable fields unencrypted in database columns. | Enrolled Email MFA contact addresses (`enrolled_email_ciphertext`, `pending_email_ciphertext`) are encrypted at rest with **AES-256-GCM** using a random per-record IV and versioned 256-bit key (`EMAIL_MFA_ENCRYPTION_KEY`, migration `202611170016_encrypt_mfa_contact.sql`), decrypted only on the server for authorized owner display or OTP dispatch. | **C** | Inspected `bantai_private.email_mfa` directly in PostgreSQL; confirmed ciphertext + IV storage is unreadable in the database while the authenticated owner can view their masked/verified contact in Account Settings. |
