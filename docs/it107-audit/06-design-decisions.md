# Design decisions for student review

Nine explicit **YOUR CALL** prompts were located. The hashing-versus-encryption note in §12 also requests a written decision.

| Handout prompt | Bantai today | Proposed decision and tradeoff | Student confirmation |
|---|---|---|---|
| §4.4 · Which password hashing algorithm and settings? | Provider-managed password writes | Retain provider-managed bcrypt where supported and verify deployed cost/settings using an isolated fixture. Check UTF-8 byte boundaries to prevent silent truncation under a character-based limit. For a wholly separate verifier, evaluate Argon2id with benchmarked memory/time settings. Do not copy real provider hashes. [Supabase password security](https://supabase.com/docs/guides/auth/password-security) | Yes, explain how settings and boundaries were verified |
| §4.9 · What makes a password strong? | Registration enforces a six-character client minimum and matching confirmation | Define Weak as below the threshold or known common/compromised, Medium as the acceptable score band and Strong as a higher guess-resistance score. Reject Weak server-side with the shared scorer, require 8–64, support passphrases, and use a privacy-preserving compromised-password check where approved. Avoid rigid composition rules as the sole score. The cost is tuning predictable feedback and testing Unicode/provider compatibility. | Yes, choose and document reproducible score thresholds |
| §5 · Why hash a security answer? | No knowledge-based questions | Hash the normalized lowercase answer with a per-record salt and a slow verifier. A hash reduces direct disclosure but low-entropy answers can still be guessed. Add isolated data, throttle answer verification and keep email/TOTP factors. [Recovery flow](../../frontend/src/lib/recoveryFlow.ts#L13) | Yes |
| §7 · Does failed CAPTCHA count as failed login? | Express records challenge rejection separately | Log and meter CAPTCHA failures by vetted source, exclude them from victim-account tiers. A bot should not be able to lock a known account by failing a CAPTCHA. Preserve uniform responses and measure effects of mixed failure sources. [Siteverify events](../../backend/src/services/turnstile.ts#L188) | Yes |
| §8.4 · Is disabling Back enough? | Route and API checks, session policy, no demonstrated post-logout back-stack proof | Enforce server revocation and check it before loading sensitive data. Clear user-scoped query cache on identity loss and revalidate browser history restoration. Keep navigation usable. This adds resume/revalidation traffic. [Middleware](../../backend/src/middleware/authenticate.ts#L114) | Yes |
| §10 · How does the verified user reach Change Password? | In-memory recovery stages with an Auth recovery session | Keep a narrowly scoped, expiring reset intent bound to user/session and verified challenge, consume exactly once with coordinated password write semantics. Verify timeout, duplicate submission and failed writer retries. Avoid storing raw passwords between calls. [Recovery flow](../../frontend/src/lib/recoveryFlow.ts#L19) | Yes |
| §13.3 · May the application DB role delete logs? | Client role direct grants restricted, aggregation writer updates counters | Give course app roles insert through constrained producers and scoped read to monitoring. Withhold UPDATE/DELETE. Use an independently privileged, governed retention path if approved. Limit retention and separate finance audit and telemetry aggregates. [Telemetry grants](../../supabase/migrations/202611150002_security_telemetry_and_incidents.sql#L41) | Yes, confirm record retention and role split |
| §14.2 · How can it run every 15 minutes? | No course monitor CLI or schedule | Run manually during demo. Document Windows Task Scheduler with 15-minute repetition and do-not-start-new-instance, or cron with a 15-minute schedule and an overlap lock. Use an explicit working directory, read-limited credentials, PHT output and failure reporting. Duplicate protection belongs at storage. | Yes, choose target scheduler |
| §15 · Can JavaScript be hidden? | Public browser bundles, server source in separate backend tree | Publish required JS/CSS. Keep server source, environment files and private CLI outside artifacts and server routes. Client validation and bundle obfuscation offer no authority. Optional source-map access and debug files require explicit deployment decisions. [Frontend hosting](../../frontend/vercel.json) | Yes, confirm equivalent public asset treatment |
| §12 note · Why hash some values and encrypt others? | Provider stores passwords, application-level field encryption for the course unverified | Passwords and answers need one-way verification. Use short-lived keyed verification for six-digit course OTPs so a leaked database alone cannot enumerate their small search space. A sensitive reference requiring owner display needs reversible authenticated encryption, with fresh nonce, protected keys and version metadata. | Yes, identify field and access purpose |
