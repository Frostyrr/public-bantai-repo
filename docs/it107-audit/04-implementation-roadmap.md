# Implementation roadmap

Effort is in focused working days for one developer. It excludes instructor turnaround and project-history calendar requirements. Scope is a disposable course environment with synthetic data. Keep rollback points phase-specific. Security fixes for verified production issues can follow independent review.

| Phase | Tasks and likely locations | Data and deployment changes | Effort and dependencies | Risks, acceptance and verification |
|---|---|---|---|---|
| 0 · Confirm requirements and prepare environment | Confirm signed proposal, retrospective workflow, UUID companion record, no-session semantics, Turnstile, bearer/CSRF equivalence, duplicate disclosures and allowed inbox. Prepare isolated app, Auth and DB, seed fixtures and separate keys. Review security config with a redacted baseline. Paths include docs/it107, frontend/vercel.json, backend/src/constants/env.ts and supabase. | Isolated Auth tenant or local stack. Synthetic fixtures, distinct origins, controlled inbox and mail credentials. Capture rollback settings and current application baselines. | 1–3 days plus instructor and setup. Start now due to process timing. | Never connect disposable tests to real finance. Acceptance requires approved scope, resolved authority design and target checks before high-impact testing. |
| 1 · Registration and validation | Course intake schema, per-field errors, semantic form layout, signed consent persistence, valid/invalid input and synthetic proposal fields. Use Register.tsx, AuthLayout.tsx, shared field component, new validated Express routes and separate migrations. | Companion profile/intake and notice version metadata. DB uniqueness and constrained state; Auth UUID unchanged. | 4–6 days after Phase 0 proposal. | Cross-service partial account creation and duplicate disclosure. Check malformed payloads, duplicate concurrency, escaped outputs, UTC/PHT birthday edge and notice record. Roll back route and preserve recoverable draft data according to agreed retention. |
| 2 · Authentication, OTP and recovery | Password phase and purpose-aware email OTP, independent recovery authorization, course answers and password policy/history. Prove every authority write route. Paths include Login.tsx, VerifyEmailPrompt.tsx, ResetPassword.tsx, recoveryFlow.ts, index.ts and Auth configuration. | Isolated challenge/answer/history/intent records where needed, provider templates, typed OTP and rate policy. Hashing through approved provider or private dedicated verifier. | 7–12 days after authority choice, some work parallel with Phase 1. | Existing OAuth, TOTP and verification boundaries. Acceptance includes no pre-OTP protected credential per agreed meaning, exact expiry/attempt/resend, no cross-purpose reuse and one successful concurrent reset. Restore isolated configuration or remove demo routing on rollback. |
| 3 · Security enforcement and protections | Trusted source/account counters, 3/6/9 rules, 900-second idle with 60-second warning, authorization, history/write checks, CSRF decision, field encryption, errors, headers, secret and sink review. Key paths are authenticate.ts, requestTiming.ts, AppContainer.tsx, frontend/vercel.json and isolated migration suite. | Atomic counter and window state, session policy configuration, ciphertext format and KMS/secret store. Keep finance and existing identities intact. | 5–8 days after Phase 2, reuse its history validation. | NAT denial, direct public paths, reconnection and signed URLs. Validate clock boundaries, source trust, role parity, confirmation replay, owner-only plaintext and real HTTP headers. Feature toggles and isolated settings support rollback. |
| 4 · Monitoring, alerts and detection | Course event taxonomy/contract, distinct read-only dashboard, idempotent mail/flags and CLI. Use admin.routes.ts, AdminDashboard.tsx, existing telemetry as design reference and private CLI outside web roots. | Append-only journal, indexes, flag key keyed by pattern/target/PHT day, restricted worker and outbox. Document scheduling and rely on manual run first. | 5–8 days after Phase 2–3 event semantics. | Event integrity, PII, duplicate alerts and query load. Verify all 17 events, 60-second passive poll, 50-row filters, four seeded patterns and contention-safe dedup. Disable worker/UI independently, retain immutable journals. |
| 5 · Documentation, verification and live demo | Build the genuine approval/checkpoint pack, Appendix B rows, privacy note and error mapping, sanitized dump, weekly journal and demo rehearsal. Clear unresolved instructor items and use [checklist](05-demo-and-submission-checklist.md). | Synthetic admin/two users and export only. | 3–5 days plus actual course calendar and assessor participation. | Insufficient history and live explainability. Acceptance requires evidence for all checks, received test mail, no secrets, a timed demo and independent code-explanation rehearsal. |

Security fixes that may safely be considered for the base app after proof include redaction, verified headers, scoped server session authorization and trustworthy audit capture. Course-only data, knowledge-based recovery and exact aggressive lockouts carry unnecessary production privacy and availability costs. Acceptance of equivalent controls belongs to the instructor.
